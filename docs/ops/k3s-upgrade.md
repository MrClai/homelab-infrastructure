# Ops: апгрейд k3s-кластера 1.32 → 1.35 (2026-07-06)

Журнал плановой операции на control plane. Формат: цель → план → исполнение → инциденты → итог.

---

## Контекст и цель

Кластер: 1 master (Raspberry Pi 5) + 2 workers (bare-metal + VM в Proxmox).

При плановой диагностике обнаружена неподдерживаемая конфигурация:

| Нода | Роль | Версия |
|---|---|---|
| homelab | control-plane | v1.32.2+k3s1 |
| k3-worker-2 | worker | v1.35.4+k3s1 |
| k3s-worker (VM101) | worker | v1.32.2+k3s1 |

Kubelet воркера **новее** apiserver на 3 минорные версии. Version skew policy Kubernetes разрешает kubelet отставать от apiserver до трёх минорок, но не обгонять. Даунгрейд kubelet не поддерживается → единственный путь — апгрейд control plane.

**Цель:** все ноды на одной минорной версии (1.35), без потери данных и без простоя рабочих нагрузок.

## Ограничения, учтённые в плане

- **Control plane апгрейдится строго по одной минорке** (1.32 → 1.33 → 1.34 → 1.35): апгрейд-путь и миграции схемы datastore тестируются только между соседними версиями; код миграций со старых форматов из новых релизов удаляется.
- **Бэкап datastore перед стартом**: миграция схемы — единственный необратимый шаг операции.
- **Только с локальным доступом**: канал удалённого доступа зависит от апгрейдируемой ноды.
- **Воркеры апгрейдятся после control plane**: на время работ с мастером второй воркер (VM) оставался выключен — меньше переменных при операции на control plane.

## Шаг 0 — определение datastore и бэкап

k3s на одиночном сервере по умолчанию использует SQLite через kine (трансляция etcd API в SQL); embedded etcd включается только для HA. Тип datastore определён фактом, а не предположением:

```bash
sudo ls -la /var/lib/rancher/k3s/server/db/
# state.db + state.db-wal + state.db-shm (свежие) → боевой datastore SQLite
# каталог etcd/ — пустой артефакт раннего запуска (один файл, дата 4-месячной давности)
```

Копировать `state.db` у работающего k3s нельзя: в WAL-режиме часть данных находится в `-wal` файле, копия на лету неконсистентна. Корректная процедура:

```bash
sudo systemctl stop k3s
sudo tar -czf ~/k3s-server-backup-$(date +%F).tar.gz -C /var/lib/rancher/k3s server
sudo systemctl start k3s
```

Архивируется каталог `server/` целиком: кроме БД там TLS-сертификаты и токены кластера — без них restore неполный. При остановке k3s рабочие нагрузки продолжают работать: data plane (kubelet, контейнеры) не зависит от живости apiserver.

## Шаги 1–3 — апгрейд master

Каждый прыжок — тем же install-скриптом с фиксацией канала (не latest):

```bash
curl -sfL https://get.k3s.io | INSTALL_K3S_CHANNEL=v1.33 sh -   # затем v1.34, v1.35
```

После каждого прыжка — проверка:

```bash
kubectl get nodes                      # мастер Ready на целевой версии
kubectl get pods -A | grep -v Running  # нет новых аварий
```

Прыжки 1.32→1.33.13 и 1.33→1.34.9 — чисто. Ожидаемое поведение: apiserver недоступен ~30–60 с на прыжок, поды не прерываются; k3s перезапускает встроенные helm-джобы (Completed — норма).

## Инцидент 1: регрессия helm-джобы Traefik после прыжка на 1.35

**Симптом:** `helm-install-traefik` в CrashLoopBackOff после третьего прыжка (на прыжках 1–2 отрабатывала).

**Диагностика:** `kubectl logs` показал точную причину: k3s 1.35 привёз чарт Traefik 40.1.3 (Traefik 3.x, мажорный скачок с 2.x), который требует новые CRD — `Error: Required CRDs are missing`. CRD-джоба (`helm-install-traefik-crd`) отработала ещё на прыжке 1.33 и на 1.35 не перезапустилась — гонка двух джоб-инсталляторов.

**Фикс:** удалить обе джобы — helm-controller k3s пересоздаёт их в правильном порядке:

```bash
kubectl delete job -n kube-system helm-install-traefik-crd helm-install-traefik
```

**Результат:** обе джобы Completed, Traefik штатно обновлён 2.x → 3.x, маршруты проверены вручную (UI Grafana и ArgoCD). Пользовательский трафик в процессе не прерывался: падала джоба-инсталлятор, а не сам ingress-контроллер.

## Инцидент 2: «сломался ArgoCD» — оказался DNS-дефектом сети

**Симптом:** после апгрейда ArgoCD UI не открывается: `DNS_PROBE` — имя не резолвится.

**Диагностика:** ошибка происходит до кластера (браузер не превратил имя в IP → Traefik/поды не участвовали). Проверка `nslookup` показала парадокс: DNS-сервер сети отвечает NXDOMAIN на **все** homelab-имена, при этом Grafana открывается. Разгадка — в hosts-файле рабочей машины: часть записей была прибита там на этапе первичной настройки, записи для ArgoCD среди них не было. На роутере DNS-записей не оказалось вовсе.

**Root cause:** задача «настроить DNS records» ранее была закрыта по симптому («работает у меня»), а не по сути. Апгрейд к дефекту отношения не имел — корреляция, не причинность.

**Фикс:** записи заведены на роутере (OpenWRT: DHCP and DNS → Hostnames), проверены с флашем DNS-кэша. Задача переоткрыта: перенести оставшиеся записи, вычистить hosts-файл (один источник правды).

**Урок:** критерий готовности сетевой настройки — проверка с устройства, где настройка не делалась.

## Шаг 4 — апгрейд агента VM101

Агент, в отличие от control plane, апгрейдится одним прыжком: он stateless — нет datastore и миграций, ограничение только skew policy (после апгрейда мастера kubelet 1.32 при apiserver 1.35 — граница поддерживаемого, апгрейжен сразу).

```bash
curl -sfL https://get.k3s.io | INSTALL_K3S_CHANNEL=v1.35 \
  K3S_URL=https://<master>:6443 K3S_TOKEN=<токен из /var/lib/rancher/k3s/server/token> sh -
```

`K3S_URL` обязателен: без него install-скрипт ставит **сервер**, и нода попытается стать вторым мастером.

Два сбоя по пути:
- **Download failed** (обрыв закачки бинарника с GitHub) → повторный запуск: install-скрипт идемпотентен, приводит систему к целевому состоянию.
- **invalid token format** → токен перенесён обрезанным; исправлен из первоисточника — файла `/var/lib/rancher/k3s/server/token` на мастере. Правило: креды и конфиги копируются из файлов.

## Итог

```
NAME          STATUS   ROLES                  VERSION
homelab       Ready    control-plane,master   v1.35.6+k3s1
k3-worker-2   Ready    <none>                 v1.35.4+k3s1
k3s-worker    Ready    <none>                 v1.35.6+k3s1
```

- Version skew устранён; разница патчей 1.35.6/1.35.4 внутри минорки поддерживается.
- Простоя рабочих нагрузок не было (проверено доступностью UI в процессе).
- Побочные результаты: Traefik 2.x → 3.x; найден и починен DNS-дефект сети; под, висевший в Terminating 109 дней (мёртвый kubelet не подтверждал удаление), рассосался с возвращением ноды.
- Заведён технический долг: токен присоединения хранился в открытом виде в юнит-файле воркера → пункт в hardening-backlog (права на env-файл, ротация токена).

## Чем это отличалось бы в production

Change window и уведомления; прогон на staging-кластере; drain нод при апгрейде kubelet (здесь пропущен осознанно — single-replica сервисы); автоматизированные smoke-тесты вместо ручной проверки UI; HA control plane для rolling-апгрейда серверов; секреты присоединения — в секрет-менеджере с ротацией.

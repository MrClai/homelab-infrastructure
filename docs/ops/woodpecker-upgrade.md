# Ops: мажорное обновление Woodpecker CI 2.8.3 → 3.18.1 (2026-09-19)

Журнал плановой операции на CI-сервере. Формат: цель → план → исполнение → инциденты → итог.
Команды дополнены рекомендациями для повторения операции; неподтверждённые проверки
отмечены отдельно. В конце — порядок следующих обновлений и отката.

---

## Контекст и цель

Woodpecker CI (server + agent) развёрнут через Docker Compose на отдельном хосте рядом с Gitea.
База — SQLite в именованном volume, смонтированном в `/var/lib/woodpecker`.
Агент использует docker-бэкенд (`/var/run/docker.sock`).

**Цель:** перейти на актуальную ветку 3.x с сохранением пользователей, репозиториев, секретов
и истории pipeline; не ломать существующие `.woodpecker.yml`.

## Условия перехода и требования к повторению

- **Мажорный переход необратим для БД.** Миграции схемы применяются автоматически при первом
  старте v3; запуск старого сервера на изменённой схеме не является безопасным откатом.
  План отката включает восстановление данных из бэкапа до миграции и старых образов.
- **Server и agent обновляются вместе.** Агент 2.x не подключается к серверу 3.x по gRPC.
- **Переход выполнен с 2.8.3 сразу на 3.18.1.** Миграции применил новый сервер.
  Для следующего обновления допустимый маршрут нужно сверять с release notes и migration guide;
  статус «последний релиз ветки» сам по себе не гарантирует совместимость.
- **Синтаксис pipeline.** В 3.0 устаревшие в 2.x конструкции стали ошибками
  (`secrets:` в шаге, `environment` списком, `group:`, `pipeline:`/`platform:`/`branches:`,
  `when: environment:`, `includes`/`excludes` в фильтрах). Конфиги проверяются до обновления.
- **Переименованные переменные окружения** (`WOODPECKER_WEBHOOK_HOST` → `WOODPECKER_EXPERT_WEBHOOK_HOST`,
  вместо `WOODPECKER_ROOT_PATH`/`WOODPECKER_ROOT_URL` используется `WOODPECKER_HOST`) —
  сверка с compose-файлом.
- **Webhook-токены изменились в v3.** Migration guide требует обновить существующие
  подключения через `Repair all` в административных настройках и проверить настоящий push.

Основание для проверки совместимости — [официальный migration guide](https://woodpecker-ci.org/migrations).

## Шаг 0 — инвентаризация и бэкап

Имя volume определяется из фактического конфига, а не подставляется по памяти:

```bash
docker inspect woodpecker-server --format '{{range .Mounts}}{{if eq .Destination "/var/lib/woodpecker"}}{{.Type}} {{.Name}} {{.Source}}{{end}}{{end}}'
docker compose config --volumes
docker volume ls | grep woodpecker
```

До остановки нужно записать фактические image ID/digest server и agent, подготовить доступ
к старым образам и сохранить Compose вместе с используемыми `.env` и файлами секретов.
Их копии и архив БД хранятся вне Git с ограниченным доступом. Compose с `latest` не фиксирует
версию для отката. Завершить активные pipeline и приостановить отправку новых заданий.

Бэкап — при остановленном сервере (SQLite должна быть консистентной).
В примере `<volume_из_config>` заменяется подтверждённым именем существующего volume;
сначала проверить его через `docker volume inspect`. Не использовать `down -v`: это удалит данные.

```bash
docker compose down
cp docker-compose.yml docker-compose.yml.bak-2.8.3
docker run --rm -v <volume_из_config>:/data:ro -v "$PWD":/backup alpine \
  tar czf /backup/woodpecker-data-2.8.3.tgz -C /data .
tar tzvf woodpecker-data-2.8.3.tgz     # в архиве должен быть woodpecker.sqlite ненулевого размера
```

`tar tzvf` подтверждает наличие файлов и помогает обнаружить пустой архив.
Восстановление из этого архива в отдельный volume в рамках операции не проверялось.
Сохранность данных после успешной миграции не заменяет тест отката.

## Шаг 1 — проверка pipeline на совместимость

`.woodpecker.yml` этого репозитория уже использует синтаксис, совместимый с v3:
`when` списком с `event`, `steps` списком, секреты не используются. Правок не потребовалось.

## Шаг 2 — смена образов и старт

```yaml
woodpecker-server:
  image: woodpeckerci/woodpecker-server:v3.18.1
woodpecker-agent:
  image: woodpeckerci/woodpecker-agent:v3.18.1
```

Точный тег вместо `latest`/`v3` фиксирует выбранный релиз. Для фиксации конкретного
содержимого образа следует также сохранить digest: тег сам по себе не запрещает перезапись.

```bash
docker compose pull
docker compose up -d
docker compose logs -f woodpecker-server
```

## Инцидент 1: `attempt to write a readonly database`

**Симптом:** сервер в цикле перезапусков, в логе
`migration cron-without-sec failed: sync new models failed: attempt to write a readonly database`.

**Диагностика:**

```bash
docker image inspect -f '{{.Config.User}}' woodpeckerci/woodpecker-server:v3.18.1   # woodpecker
docker run --rm -v <volume>:/data alpine ls -lan /data                               # 0 0 (root)
```

UID/GID пользователя из образа извлечён без запуска сервера — из `/etc/passwd` образа:

```bash
cid=$(docker create woodpeckerci/woodpecker-server:v3.18.1)
docker cp "$cid":/etc/passwd - | tar -xO | grep woodpecker    # woodpecker:x:1000:1000
docker rm "$cid"
```

**Root cause:** образ v2 работал от root, и файлы в volume принадлежали root. Образ v3 запускается
от непривилегированного пользователя `woodpecker` (1000:1000) и не может писать ни в
`woodpecker.sqlite`, ни в каталог, где SQLite создаёт журнал.

**Фикс:** передать владение данными пользователю из образа. При повторении сначала
остановить сервер и сохранить бэкап; исходный архив до миграции не перезаписывать:

```bash
docker compose stop woodpecker-server
# До chown проверить бэкап и фактическое имя volume.
docker run --rm -v <volume>:/data alpine sh -c 'chown -R 1000:1000 /data && ls -lan /data'
docker compose up -d woodpecker-server
```

Миграции прошли, сервер стартовал: `starting Woodpecker server with version '3.18.1'`.
Время изменения основного файла `woodpecker.sqlite` до фикса не изменилось, но этого
недостаточно для доказательства отсутствия записей. Например, в режиме WAL транзакции
могут находиться в отдельном файле. Отсутствие изменений базы отдельно не проверялось.
См. [описание WAL в SQLite](https://sqlite.org/wal.html#how_wal_works).

Альтернатива — `user: "0:0"` в compose — отклонена: возвращает запуск от root и теряет смысл изменения в образе.

## Инцидент 2: пустой «бэкап» из-за угаданного имени volume

**Симптом:** рядом с рабочим volume появился второй, пустой.

**Root cause:** первая команда бэкапа была выполнена с именем volume «по шаблону», которое не совпало
с фактическим. `docker run -v <несуществующий_volume>:/data` не падает — Docker молча создаёт новый
пустой volume, и архивируется пустота. Код возврата при этом успешный.

**Фикс:** имя взято из `docker compose config`, бэкап переснят, содержимое архива проверено `tar tzvf`,
лишний volume удалён.

**Урок:** в командах бэкапа и восстановления — только имена, подтверждённые выводом системы;
проверяется содержимое архива, а не код возврата.

## Инцидент 3: агент `Unauthenticated` после рестарта сервера

**Симптом:** после задания постоянного `WOODPECKER_GRPC_SECRET` агент логирует
`access token is invalid: token signature is invalid`.

**Причина:** до этого сервер при каждом старте генерировал случайный gRPC-секрет. Агент держал токен
сессии, подписанный старым ключом; после рестарта сервера с новым ключом подпись перестала сходиться.
Агент переавторизуется сам через `WOODPECKER_AGENT_SECRET`, но с backoff до нескольких минут.

**Фикс:** `docker compose up -d --force-recreate woodpecker-agent` — агент сразу получил новый токен.
Это ускорило восстановление соединения. При неизменном `WOODPECKER_AGENT_SECRET`
перезапуск не обязателен: агент должен переавторизоваться самостоятельно.
Постоянный ключ и его поведение описаны в
[документации сервера](https://woodpecker-ci.org/docs/administration/configuration/server#grpc_secret).

## Итог

- Server и agent на v3.18.1, оба `healthy`; миграции БД применены, данные сохранены.
- `WOODPECKER_GRPC_SECRET` задан постоянным (раньше генерировался на каждый старт).
- Проверенный синтаксис pipeline `homelab-infrastructure` не потребовал правок.
- После обновления тестовый push в `Igor/land` создал конвейер №9
  `Verify Woodpecker webhook after upgrade` на ветке `main` (коммит `0adf19a736…`).
  На скриншоте Woodpecker все шаги — `clone`, `build-site`, `build-and-push` — зелёные.
  В логе видны `docker build` и `docker push` образа с тегом SHA этого коммита.
  Это подтверждает работу цепочки от push до публикации образа после миграции.

После перехода на v3 администратор выполнил `Repair all` в Woodpecker; это подтверждено
его сообщением 19 сентября 2026 года. Конвейер №9 после push подтвердил работу webhook
и CI на примере `land`.

**Границы проверки:** отдельный вывод доставки webhook из Gitea не сохранялся.
Тестовый образ не выбирался в Kubernetes; это не требовалось для проверки CI после
обновления. Восстановление бэкапа не тестировалось.
У агента при образе с тегом `v3.18.1` в логе была строка версии `next-128113e5ef`;
соответствие сборки релизу отдельно не выяснялось.


## Инструкция для следующих обновлений

1. Прочитать release notes и migration guide для исходной и целевой версий, проверить
   поддерживаемый маршрут обновления и изменения webhook, pipeline и переменных окружения.
2. Проверить конфиги всех активных репозиториев, включая используемые секреты и плагины.
3. Записать image ID/digest обоих запущенных контейнеров, сохранить старые образы,
   Compose, `.env` и используемые файлы секретов вне публичного репозитория.
4. Пока контейнер существует, определить volume через `docker inspect`; сверить с Compose
   и `docker volume inspect`. Не угадывать имя по шаблону.
5. Завершить активные pipeline, приостановить новые задания. `docker compose down` без `-v`,
   затем бэкап всего volume, проверка содержимого архива и контрольной суммы.
   Для проверенного плана отката — восстановление в отдельный тестовый volume.
6. Загрузить целевые образы server и agent. До первого запуска проверить UID/GID сервера
   и владельцев данных; при необходимости изменить владельца при остановленном сервере.
7. Указать выбранные версии обоих образов и запустить `docker compose up -d`.
8. Проверить миграции и запуск HTTP/gRPC без циклических рестартов, затем подключение агента.
9. При переходе 2.x → 3.x выполнить `Repair all` в административных настройках Woodpecker
   для обновления webhook существующих репозиториев.
10. Проверить вход через Gitea, наличие репозиториев и секретов, статус агента и контейнеров.
    Сделать настоящий тестовый push: webhook доставлен, pipeline автоматически создан,
    clone и шаги завершились успешно. Проверку `land` включить отдельно: его pipeline
    использует registry secrets и Docker socket, в отличие от pipeline инфраструктуры.
11. При неустранимой ошибке выполнить процедуру отката ниже.

### Порядок отката

Это подготовленная процедура; её выполнение в этой операции не подтверждено.

1. Остановить server и agent через `docker compose down` без `-v`. Не запускать v2
   на volume с уже мигрировавшей БД.
2. Сохранить отдельную копию состояния после неудачного обновления для диагностики.
   Исходный бэкап до миграции оставить неизменным.
3. Создать новый пустой volume и восстановить в него весь архив до миграции с владельцами
   и правами файлов. Не распаковывать старую БД поверх новой: там могут остаться файлы
   журналов или другие данные новой версии. Проверить состав восстановленного volume.
4. Вернуть сохранённую конфигурацию и зависимые файлы. Указать точные старые образы обоих
   компонентов по записанным digest либо использовать заранее сохранённые образы.
   Одного возврата Compose с `latest` недостаточно.
5. В Compose явно подключить восстановленный volume к `/var/lib/woodpecker` сервера
   и проверить итоговую конфигурацию. Старый volume сохранить до завершения проверок.
6. Запустить старые server и agent, проверить БД, вход и соединение агента. Если webhook
   уже менялись для v3, восстановить подключения репозиториев средствами старой версии.
7. Повторить настоящий тестовый push. Только после успешной проверки возобновить задания.

## Чем это отличалось бы в production

Обновление сначала на staging-инстансе с копией базы; change window и уведомление команд, чьи
pipeline затронуты; проверенный restore до изменения рабочей системы и автоматический
прогон тестового pipeline после обновления. Выбор SQLite или PostgreSQL определяется
нагрузкой, топологией и требованиями к восстановлению; смена СУБД сама по себе не обеспечивает
надёжность. Секреты server/agent — в секрет-менеджере с ротацией; доступ к gRPC ограничен,
а при передаче по недоверенной сети используется TLS.

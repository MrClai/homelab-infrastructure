# Architecture Decision Records

Документ фиксирует ключевые архитектурные решения homelab: что выбрано, почему, какие альтернативы рассматривались и какие последствия принесло решение.

---

## ADR-001: k3s как Kubernetes-дистрибутив

**Контекст:** нужен Kubernetes-кластер на реальном железе — Raspberry Pi 5 как control plane и x86-ноды как workers. Цель — изучить реальные принципы работы кластера, а не имитировать их через minikube или kind.

**Решение:** k3s

**Альтернативы:**
- *kubeadm* — стандартный способ поднять "полный" Kubernetes. Тяжелее, требует ручной настройки CNI, CoreDNS и других компонентов. Хорош для изучения внутренностей, но избыточен для homelab на Pi.
- *k0s* — аналогично лёгкий дистрибутив, но меньше документации и сообщества на момент выбора.
- *minikube / kind* — только для локальной разработки, не для реального железа.

**Причина выбора k3s:**
- из коробки включает CoreDNS, Traefik, metrics-server и local-path-provisioner — не нужно собирать кластер по частям с нуля;
- хорошо работает на ARM (Pi5) и x86 одновременно;
- API-совместим с upstream Kubernetes — навыки переносятся на production-кластеры;
- активное сообщество и документация.

**Последствия:**
- кластер поднялся быстро, можно было сразу фокусироваться на workload, а не на настройке кластера;
- текущий control-plane — одна нода, нет отказоустойчивости; это осознанный trade-off для homelab.

## ADR-002: Proxmox VE как гипервизор

**Контекст:** часть сервисов должна жить на виртуальных машинах, а не в Kubernetes — Gitea, Woodpecker CI, OpenBao, Ansible control node. Нужен гипервизор на x86-железе (Digma PRO).

**Решение:** Proxmox VE

**Альтернативы:**
- *VMware ESXi* — мощный, но платный и закрытый. Избыточен для homelab.
- *bare-metal без гипервизора* — проще, но нет изоляции между сервисами и нет возможности управлять через IaC.
- *libvirt / KVM напрямую* — более низкоуровневый контроль, но без UI и сложнее автоматизировать через Terraform.

**Причина выбора Proxmox:**
- open-source, бесплатный для homelab;
- есть Terraform-провайдер (bpg/proxmox) — VM описываются кодом, а не кликами;
- удобный UI для отладки и мониторинга;
- хорошо известен в DevOps-сообществе.

**Последствия:**
- все VM (101–105) описаны в Terraform, state хранится в MinIO — воспроизводимая инфраструктура;
- изоляция сервисов по VM упрощает troubleshooting и обновления.

## ADR-003: OpenBao как secrets manager

**Контекст:** секреты (пароли, токены) не должны храниться в Git или в values.yaml. Нужен централизованный secrets manager с поддержкой Kubernetes-аутентификации.

**Решение:** OpenBao

**Альтернативы:**
- *HashiCorp Vault* — де-факто стандарт, но в 2023 году сменил лицензию на BSL (Business Source License). Для homelab это не критично, но OpenBao — прямой open-source форк с совместимым API.
- *K8s Secrets* — просто, но base64 — не шифрование. Secrets попадают в etcd без дополнительной защиты. Нет audit log, нет rotation.
- *Sealed Secrets / External Secrets Operator* — хорошие инструменты, но требуют внешнего backend. OpenBao сам является этим backend.

**Причина выбора OpenBao:**
- API-совместим с Vault — навыки и документация переносятся;
- open-source без лицензионных ограничений;
- поддерживает Kubernetes auth — pod получает секрет через ServiceAccount без хранения credentials в образе;
- Vault Agent Injector монтирует секрет как файл в pod — не через переменные окружения.

**Последствия:**
- Grafana получает adminPassword через Injector из файла, пароль не в values.yaml и не в Git;
- Alertmanager читает SMTP-пароль из K8s Secret через file mount — это промежуточное решение, перенос в OpenBao запланирован;
- все секреты в одном месте с audit log.

## ADR-004: ArgoCD для GitOps

**Контекст:** деплой в Kubernetes делался вручную через `kubectl apply`. Нужен способ сделать Git источником желаемого состояния и автоматически синхронизировать кластер.

**Решение:** ArgoCD

**Альтернативы:**
- *Flux CD* — аналогичный GitOps-инструмент, pull-based. Меньше UI, более декларативная конфигурация через CRD. Хорошая альтернатива, но меньше визуальной обратной связи.
- *manual kubectl apply в CI* — проще, но нет drift detection: кто-то может изменить ресурс руками, и CI об этом не узнает.
- *Helm без GitOps* — управляет релизами, но не следит за расхождением между Git и кластером.

**Причина выбора ArgoCD:**
- Git — единственный источник правды для состояния кластера;
- drift detection: ArgoCD замечает ручные изменения в кластере и может их откатить;
- UI показывает дерево ресурсов и статус синхронизации — удобно для отладки;
- хорошо интегрируется с Gitea и Woodpecker CI.

**Последствия:**
- ручные `kubectl apply` остались только для отладки, не для постоянных изменений;
- test workload синхронизируется через ArgoCD, drift detection проверен;
- текущий debt: ArgoCD Dex в ImagePullBackOff — не критично для функционала, но требует фикса.

## ADR-005: Terraform для управления VM в Proxmox

**Контекст:** VM в Proxmox создавались вручную через UI. Нужен воспроизводимый способ создавать и описывать инфраструктуру — чтобы можно было восстановить или пересоздать VM без ручных шагов.

**Решение:** Terraform с провайдером bpg/proxmox, state в MinIO

**Альтернативы:**
- *Proxmox UI / CLI вручную* — быстро, но не воспроизводимо. Нет истории изменений.
- *Pulumi* — современная альтернатива Terraform, code-first подход. Меньше экосистема для Proxmox на момент выбора.

Terraform и Ansible используются вместе, но решают разные задачи: Terraform создаёт VM как инфраструктурный ресурс (provisioning), Ansible настраивает ОС и сервисы внутри уже созданной VM (configuration management). Это стандартное разделение ответственности в production.

**Причина выбора Terraform:**
- декларативный подход: описываешь желаемое состояние, Terraform сам считает diff;
- state в MinIO (S3-compatible) — не локальный файл, доступен с разных машин;
- провайдер bpg/proxmox зрелый и хорошо документирован;
- стандарт индустрии — навык напрямую применим в работе.

**Последствия:**
- все VM (101–105) в state, `terraform plan` = No changes — инфраструктура описана и синхронизирована;
- новые VM создаются через `terraform apply`, не через UI;
- SSH-ключи передаются через cloud-init в коде, а не через `ssh-copy-id` вручную.

## ADR-006: MinIO как S3-compatible storage

**Контекст:** нужен backend для Terraform state и хранилище для Docker Registry. Использовать внешний S3 (AWS) не хочется — homelab должен быть self-hosted.

**Решение:** MinIO на Pi5

**Альтернативы:**
- *AWS S3* — надёжно, но внешняя зависимость и стоимость. Противоречит идее self-hosted homelab.
- *локальный файл для Terraform state* — просто, но не работает при работе с нескольких машин и нет версионирования.
- *Ceph* — мощный distributed storage, но избыточен для homelab на одном хосте.

**Причина выбора MinIO:**
- S3-совместимый API — работает со стандартными клиентами (Terraform S3 backend, Docker Registry);
- self-hosted, данные не уходят за пределы домашней сети;
- простая установка и администрирование.

**Последствия:**
- Terraform state хранится в `terraform-state/homelab/terraform.tfstate` в MinIO;
- Docker Registry использует MinIO как backend для образов;
- MinIO на Pi5 — SPOF, поэтому нужен backup.

## ADR-007: GL-MT6000 как основной роутер сети

**Контекст:** нет единой точки управления сетью — DHCP, DNS и firewall размазаны по разным местам. DNS-записи для homelab-сервисов ведутся вручную, нет централизованного firewall с зонами.

**Решение:** GL-MT6000 с OpenWRT как основной gateway

**Альтернативы:**
- *OPNsense на VM в Proxmox (Hopper)* — рассматривался и разворачивался. Проблема: тройной NAT (МГТС → Hopper → OPNsense) — домашние устройства и Wi-Fi оказались за дополнительным слоем NAT, что нарушало нормальную работу сети. Отброшен.
- *pfSense на отдельном x86* — аналогичная проблема с NAT при текущей топологии сети.
- *Pi5 как router* — смешивает роли: Pi5 уже control plane k3s и NFS-хост.

**Причина выбора GL-MT6000 с OpenWRT:**
- OpenWRT — Linux под капотом, firewall zones, DNS, DHCP описываются через UCI или напрямую в конфигах;
- единая точка управления: DHCP, DNS-записи для homelab-сервисов, firewall — всё в одном месте;
- GL-MT6000 — мощное железо с официальной поддержкой OpenWRT;
- host firewall (UFW на каждой ноде) остаётся вторым слоем защиты.

**Последствия:**
- DNS-записи для всех homelab-сервисов (Gitea, Grafana, ArgoCD и др.) резолвятся через GL-MT6000;
- FRP продолжает работать после миграции — внешний доступ не пострадал;
- следующий шаг: описать firewall zones (LAN, homelab/servers, guest, VPN, WAN).

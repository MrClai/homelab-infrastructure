# Architecture Decision Records

Документ фиксирует ключевые архитектурные решения homelab: что выбрано, почему, какие альтернативы рассматривались и какие последствия принесло решение.

---

## ADR-001: k3s как Kubernetes-дистрибутив

**Контекст:** нужен Kubernetes-кластер на реальном железе — Raspberry Pi 5 как control plane и x86-ноды как workers. Цель — изучить реальные принципы работы кластера, а не имитировать их через minikube или kind.

**Решение:** k3s

**Альтернативы:**
- *kubeadm* — стандартный способ поднять "полный" Kubernetes. Тяжелее, требует ручной настройки CNI, CoreDNS и других компонентов. Хорош для изучения внутренностей, но избыточен для homelab на Pi.
- *k0s* — аналогично лёгкий дистрибутив, но меньше документации и сообщества на момент выбора.
- *minikube / kind* — только для локальной разработки, не для реального железа.

**Причина выбора k3s:**
- из коробки включает CoreDNS, Traefik, metrics-server и local-path-provisioner — не нужно собирать кластер по частям с нуля;
- хорошо работает на ARM (Pi5) и x86 одновременно;
- API-совместим с upstream Kubernetes — навыки переносятся на production-кластеры;
- активное сообщество и документация.

**Последствия:**
- кластер поднялся быстро, можно было сразу фокусироваться на workload, а не на настройке кластера;
- текущий control-plane — одна нода, нет отказоустойчивости; это осознанный trade-off для homelab.

## ADR-002: Proxmox VE как гипервизор

**Контекст:** часть сервисов должна жить на виртуальных машинах, а не в Kubernetes — Gitea, Woodpecker CI, OpenBao, Ansible control node. Нужен гипервизор на x86-железе (Digma PRO).

**Решение:** Proxmox VE

**Альтернативы:**
- *VMware ESXi* — мощный, но платный и закрытый. Избыточен для homelab.
- *bare-metal без гипервизора* — проще, но нет изоляции между сервисами и нет возможности управлять через IaC.
- *libvirt / KVM напрямую* — более низкоуровневый контроль, но без UI и сложнее автоматизировать через Terraform.

**Причина выбора Proxmox:**
- open-source, бесплатный для homelab;
- есть Terraform-провайдер (bpg/proxmox) — VM описываются кодом, а не кликами;
- удобный UI для отладки и мониторинга;
- хорошо известен в DevOps-сообществе.

**Последствия:**
- все VM (101–105) описаны в Terraform, state хранится в MinIO — воспроизводимая инфраструктура;
- изоляция сервисов по VM упрощает troubleshooting и обновления.

## ADR-003: OpenBao как secrets manager

**Контекст:** секреты (пароли, токены) не должны храниться в Git или в values.yaml. Нужен централизованный secrets manager с поддержкой Kubernetes-аутентификации.

**Решение:** OpenBao

**Альтернативы:**
- *HashiCorp Vault* — де-факто стандарт, но в 2023 году сменил лицензию на BSL (Business Source License). Для homelab это не критично, но OpenBao — прямой open-source форк с совместимым API.
- *K8s Secrets* — просто, но base64 — не шифрование. Secrets попадают в etcd без дополнительной защиты. Нет audit log, нет rotation.
- *Sealed Secrets / External Secrets Operator* — хорошие инструменты, но требуют внешнего backend. OpenBao сам является этим backend.

**Причина выбора OpenBao:**
- API-совместим с Vault — навыки и документация переносятся;
- open-source без лицензионных ограничений;
- поддерживает Kubernetes auth — pod получает секрет через ServiceAccount без хранения credentials в образе;
- Vault Agent Injector монтирует секрет как файл в pod — не через переменные окружения.

**Последствия:**
- Grafana получает adminPassword через Injector из файла, пароль не в values.yaml и не в Git;
- Alertmanager читает SMTP-пароль из K8s Secret через file mount — это промежуточное решение, перенос в OpenBao запланирован;
- все секреты в одном месте с audit log.

## ADR-004: ArgoCD для GitOps

**Контекст:** деплой в Kubernetes делался вручную через `kubectl apply`. Нужен способ сделать Git источником желаемого состояния и автоматически синхронизировать кластер.

**Решение:** ArgoCD

**Альтернативы:**
- *Flux CD* — аналогичный GitOps-инструмент, pull-based. Меньше UI, более декларативная конфигурация через CRD. Хорошая альтернатива, но меньше визуальной обратной связи.
- *manual kubectl apply в CI* — проще, но нет drift detection: кто-то может изменить ресурс руками, и CI об этом не узнает.
- *Helm без GitOps* — управляет релизами, но не следит за расхождением между Git и кластером.

**Причина выбора ArgoCD:**
- Git — единственный источник правды для состояния кластера;
- drift detection: ArgoCD замечает ручные изменения в кластере и может их откатить;
- UI показывает дерево ресурсов и статус синхронизации — удобно для отладки;
- хорошо интегрируется с Gitea и Woodpecker CI.

**Последствия:**
- ручные `kubectl apply` остались только для отладки, не для постоянных изменений;
- test workload синхронизируется через ArgoCD, drift detection проверен;
- ArgoCD проверен как часть общего состояния GitOps; отдельный operational debt по нему в текущей документации не фиксируется.

## ADR-005: Terraform для управления VM в Proxmox

**Контекст:** VM в Proxmox создавались вручную через UI. Нужен воспроизводимый способ создавать и описывать инфраструктуру — чтобы можно было восстановить или пересоздать VM без ручных шагов.

**Решение:** Terraform с провайдером bpg/proxmox, state в MinIO

**Альтернативы:**
- *Proxmox UI / CLI вручную* — быстро, но не воспроизводимо. Нет истории изменений.
- *Pulumi* — современная альтернатива Terraform, code-first подход. Меньше экосистема для Proxmox на момент выбора.

Terraform и Ansible используются вместе, но решают разные задачи: Terraform создаёт VM как инфраструктурный ресурс (provisioning), Ansible настраивает ОС и сервисы внутри уже созданной VM (configuration management). Это стандартное разделение ответственности в production.

**Причина выбора Terraform:**
- декларативный подход: описываешь желаемое состояние, Terraform сам считает diff;
- state в MinIO (S3-compatible) — не локальный файл, доступен с разных машин;
- провайдер bpg/proxmox зрелый и хорошо документирован;
- стандарт индустрии — навык напрямую применим в работе.

**Последствия:**
- все VM (101–105) в state, `terraform plan` = No changes — инфраструктура описана и синхронизирована;
- новые VM создаются через `terraform apply`, не через UI;
- SSH-ключи передаются через cloud-init в коде, а не через `ssh-copy-id` вручную.

## ADR-006: MinIO как S3-compatible storage

**Контекст:** нужен backend для Terraform state. Использовать внешний S3 (AWS) не хочется — homelab должен быть self-hosted.

**Решение:** MinIO на Pi5

**Альтернативы:**
- *AWS S3* — надёжно, но внешняя зависимость и стоимость. Противоречит идее self-hosted homelab.
- *локальный файл для Terraform state* — просто, но не работает при работе с нескольких машин и нет версионирования.
- *Ceph* — мощный distributed storage, но избыточен для homelab на одном хосте.

**Причина выбора MinIO:**
- S3-совместимый API — работает со стандартными клиентами (Terraform S3 backend);
- self-hosted, данные не уходят за пределы домашней сети;
- простая установка и администрирование.

**Последствия:**
- Terraform state хранится в `terraform-state/homelab/terraform.tfstate` в MinIO;
- MinIO на Pi5 — SPOF, поэтому нужен backup.

**Исправление 28.07.2026:** изначальная версия этого ADR утверждала, что Docker Registry тоже использует MinIO как backend. Проверено фактом при подготовке TLS/auth для Registry (см. ADR-011) — `docker exec registry cat /etc/docker/registry/config.yml` показывает `storage: filesystem`, `rootdirectory: /var/lib/registry`, смонтированный на `/mnt/registry`. Registry пишет на локальный диск Pi5 напрямую и клиентом MinIO не является.

## ADR-007: GL-MT6000 как основной роутер сети

**Контекст:** нет единой точки управления сетью — DHCP, DNS и firewall размазаны по разным местам. DNS-записи для homelab-сервисов ведутся вручную, нет централизованного firewall с зонами.

**Решение:** GL-MT6000 с OpenWRT как основной gateway

**Альтернативы:**
- *OPNsense на VM в Proxmox (Hopper)* — рассматривался и разворачивался. Проблема: тройной NAT (МГТС → Hopper → OPNsense) — домашние устройства и Wi-Fi оказались за дополнительным слоем NAT, что нарушало нормальную работу сети. Отброшен.
- *pfSense на отдельном x86* — аналогичная проблема с NAT при текущей топологии сети.
- *Pi5 как router* — смешивает роли: Pi5 уже control plane k3s и NFS-хост.

**Причина выбора GL-MT6000 с OpenWRT:**
- OpenWRT — Linux под капотом, firewall zones, DNS, DHCP описываются через UCI или напрямую в конфигах;
- единая точка управления: DHCP, DNS-записи для homelab-сервисов, firewall — всё в одном месте;
- GL-MT6000 — мощное железо с официальной поддержкой OpenWRT;
- host firewall (UFW на каждой ноде) остаётся вторым слоем защиты.

**Последствия:**
- DNS-записи для всех homelab-сервисов (Gitea, Grafana, ArgoCD и др.) резолвятся через GL-MT6000;
- FRP продолжает работать после миграции — внешний доступ не пострадал;
- следующий шаг: описать firewall zones (LAN, homelab/servers, guest, VPN, WAN).

## ADR-008: Граница прав Terraform и политика запуска VM

**Контекст:** после старта Proxmox основные сервисные VM должны подниматься автоматически. Для этого достаточно `on_boot`, но настройка зависимого порядка через `startup` требует системного права `Sys.Modify` на корне `/`. Попытка изменить `startup` с текущей ролью Terraform завершилась HTTP 403.

**Решение:** не расширять роль Terraform до полного системного изменения `/`. Использовать `on_boot = true` для VM101–VM104, `on_boot = false` для VM105 и `started = true` для ожидаемого состояния VM после применения Terraform. Блок `startup` не использовать.

**Последствия:** Terraform сохраняет принцип least privilege и может управлять автозапуском основных VM. Зависимый порядок запуска не описан в Terraform и при необходимости выполняется как отдельная операционная процедура. Для текущего single-node homelab это приемлемый компромисс.

**Проверка:** фактическое значение подтверждается через `qm config <VMID>`, а отсутствие расхождений — повторным `terraform plan`.

## ADR-009: MinIO остаётся вне кластера k3s

**Контекст:** MinIO работает на Pi5 как systemd-сервис и хранит Terraform state (`terraform-state/homelab/terraform.tfstate`), Raft-снапшоты OpenBao и данные, с которых был выполнен проверенный restore. Подтверждённые клиенты MinIO: VM101 (Terraform S3 backend), Pi5 сам (`backup-minio.sh`), VM104/openbao (`backup-openbao.sh` через `mc`), VM105 (ansible-control, хост internal CA) — все за пределами кластера. WSL на ноутбуке клиентом не является: `fetch-backups-to-laptop.sh` использует `scp`, а не MinIO API напрямую. При планировании TLS возник вопрос о переносе MinIO в k3s: это дало бы декларативность через ArgoCD и автоматические сертификаты через cert-manager. Решение зафиксировано явно, потому что выгода варианта реальна и неочевидно, почему от неё отказываемся.

**Решение:** MinIO остаётся вне кластера, на Pi5. Роль сервиса — хранилище состояния и бэкапов, и она требует независимости от кластера. Дополняет ADR-006, где выбирался сам продукт; здесь фиксируется место его размещения.

**Альтернативы:**
- *MinIO в k3s через Helm или MinIO Operator* — даёт GitOps и TLS «из коробки», но создаёт циклическую зависимость и укладывает объектное хранилище поверх NFS поверх того же диска Pi5.
- *Две инсталляции по ролям* — MinIO вне кластера для state и бэкапов плюс отдельная in-cluster инсталляция под прикладные S3-нагрузки (например, chunks для Loki). Рассматривается как возможное развитие, а не как замена: разворачивается при появлении реальной потребности.

**Причина отказа от переноса в кластер:**
- циклическая зависимость: Terraform state и снапшоты OpenBao — инструменты восстановления, и внутри кластера они оказываются недоступны ровно в тот момент, когда нужны. Кластер лёг → нужен `terraform apply` или restore OpenBao → нужен state → он в MinIO → MinIO в кластере;
- сценарий не гипотетический: при апгрейде мастера 1.32 → 1.35 регрессия `helm-install-traefik` временно вывела из строя Ingress. Бэкенд внутри апгрейдящегося кластера заблокировал бы восстановление;
- отраслевое правило: хранилище состояния и бэкапов не размещается внутри системы, которую оно восстанавливает — по этой же причине Terraform-бэкенды в production выносят в отдельный аккаунт или регион;
- слоистость хранения: в кластере объекты писались бы в PV на NFS, экспортируемый с того же диска Pi5, где MinIO сейчас работает напрямую. Лишний слой без выигрыша, притом что NFS уже зафиксирован как SPOF;
- преимущества переноса компенсируются иначе: декларативность — управлением через Ansible с кодом в Git, TLS — через ADR-010.

**Последствия:**
- порядок disaster recovery линеен и не содержит колец: MinIO доступен при полностью неработающем кластере;
- MinIO не попадает под ArgoCD — drift ловится не автоматически, а через Ansible и ревью;
- TLS требует отдельного решения, автоматический выпуск через cert-manager недоступен;
- инфраструктура остаётся неоднородной: часть сервисов в кластере, часть на хостах — это осознанная плата за независимость критичного хранилища;
- решение пересматривается, если появится отдельный физический узел под кластерное хранилище или Terraform state переедет на другой бэкенд.

**Проверка:** MinIO отвечает на `192.168.1.10:9002` при остановленном k3s; `terraform plan` выполняется независимо от состояния кластера.

## ADR-010: Internal CA для TLS внутренних сервисов

**Контекст:** MinIO обслуживает клиентов по HTTP — Terraform state и Raft-снапшоты OpenBao передаются по локальной сети открытым текстом. Отсутствие TLS означает два разных дефекта: нет конфиденциальности канала и нет аутентификации сервера, то есть клиент не имеет доказательства, что подключился именно к MinIO. До сих пор HTTP был осознанно принятым компромиссом для изолированного homelab. Решение пересмотрено, потому что TLS нужен не только MinIO — Registry ждёт того же в рамках hardening, а подтверждённых клиентов уже четыре: VM101, Pi5, VM104, VM105 (см. ADR-009).

**Решение:** собственный internal CA, выпускаемый вручную через openssl. Корневой ключ RSA-4096 создаётся и хранится на VM105 (ansible-control), зашифрован парольной фразой; фраза — в KeePassXC. Корневой сертификат — 10 лет, сертификаты сервисов — 1 год. Публичная часть корня раздаётся Ansible-ролью в `/usr/local/share/ca-certificates`. Первый потребитель — MinIO, следующий — Registry.

**Альтернативы:**
- *самоподписанный сертификат на сервис* — быстрее, но требует обхода всех клиентов при каждом новом сервисе и при каждом истечении срока. При двух сервисах и четырёх клиентах это уже восемь операций вместо четырёх, дальше только хуже.
- *step-ca (Smallstep)* — полноценный CA-демон с ACME, сертификаты обновляются автоматически. Объективно лучше по эксплуатации, но скрывает механику PKI за инструментом и сам нуждается в обслуживании и бэкапе.
- *cert-manager с CA-issuer* — уже установлен в кластере, но MinIO по ADR-009 живёт вне k3s. Сертификат пришлось бы выгружать из Secret наружу скриптом — противоестественная схема.

**Причина выбора internal CA на openssl:**
- доверие раздаётся клиентам один раз, дальше новые сервисы получают сертификаты без повторного обхода — Registry закрывается за час;
- ручная сборка даёт понимание всех сущностей PKI: ключ, CSR, SAN, extensions, цепочка доверия. Одна из целей homelab — освоение технологии, а не только получение результата;
- выбор не закрывает дорогу к step-ca: последовательность «сначала собрал PKI руками, затем автоматизировал ротацию через ACME» — нормальный путь развития инфраструктуры;
- отсутствие дополнительного сервиса, который сам требует обслуживания.

**Модель угроз корневого ключа:** владелец `ca.key` может выписать валидный сертификат на любое имя, которому доверяют клиенты, и они его примут. Это не ключ от одного сервиса, а возможность выдать себя за любой сервис инфраструктуры. Меры: ключ не размещается на узле, обслуживающем трафик (VM105, не Pi5); шифруется парольной фразой (`-aes256`), фраза — отдельной записью в KeePassXC; права `0400`, каталог `0700`; в Git не попадает ни ключ, ни фраза. Принятый остаточный риск: VM105 — обычная VM без HSM и офлайн-хранения корня. В production корневой CA держат офлайн и подписывают им промежуточный.

**Последствия:**
- каждый следующий внутренний сервис получает TLS без обхода клиентов;
- появляется аутентификация сервера там, где её сейчас нет вообще;
- ротация остаётся ручной — нужен способ не пропустить срок, дата истечения зафиксирована ниже;
- добавляется критичный секрет с собственной моделью угроз;
- клиент без корневого сертификата перестаёт подключаться — при добавлении нового узла шаг раздачи доверия обязателен;
- решение пересматривается при росте числа сервисов под CA свыше пяти или если ручная ротация начнёт приводить к простоям — тогда миграция на step-ca с ACME.

**Проверка:** выполнено и подтверждено 27.07.2026. `openssl s_client -connect minio.homelab.local:9002 -CAfile ca.crt` — `Verify return code: 0 (ok)`. Docker-образ MinIO подхватил сертификаты автоматически (`/root/.minio/certs/public.crt` + `private.key`) и полностью перешёл на HTTPS — HTTP перестал обслуживаться. После переключения `terraform init -reconfigure` и `terraform plan` на VM101 вернули `No changes`. `mc ls homelab` подтверждён на Pi5 и VM104 без ошибок цепочки доверия — оба бэкап-скрипта восстановлены.

**Дата истечения листового сертификата MinIO: 27.07.2027.** При приближении срока — перевыпуск по тем же шагам, без создания нового корня.

**Подтверждение разделения зон ответственности (20.08.2026):** cert-manager, установленный в кластере, и internal CA, описанный выше, не пересекаются на практике. Ревизия показала, что cert-manager управляет ровно одним сертификатом — самоподписанным, для тестового workload внутри кластера — и не имеет отношения к MinIO/Registry, что и предполагалось при выборе internal CA (см. «Альтернативы» выше). Заодно обнаружен и удалён неиспользуемый `ClusterIssuer` для Let's Encrypt staging — заготовка под гипотетический публичный сервис на внешнем VPS, который так и не был реализован; ни один сертификат на него не ссылался. Пересоздать такой `ClusterIssuer` — вопрос нескольких минут, если публичный сервис на VPS когда-нибудь появится.

## ADR-011: TLS и basic auth для Docker Registry

**Контекст:** локальный Registry (`registry:2` на Pi5, порт `:5000`) работал без TLS и без аутентификации — любой в локальной сети мог делать `docker push`/`pull` без ограничений. При диагностике перед началом работы выяснилось два факта, повлиявших на объём работы: во-первых, ADR-006 ошибочно связывал Registry с MinIO как S3-backend — по факту (`docker exec registry cat /etc/docker/registry/config.yml`) хранилище работает через `filesystem`, том `/mnt/registry`, значит TLS для Registry — независимая задача, не расширение доверия MinIO. Во-вторых, сам контейнер держался на голом `docker run --restart always`, без `docker-compose` и без systemd-юнита — единственный сервис в проекте, управляемый не декларативно.

**Решение:** тот же internal CA, что и для MinIO (ADR-010) — отдельный листовой сертификат `registry.homelab.local` / `192.168.1.10`, срок 1 год. Аутентификация — `htpasswd` со схемой bcrypt (единственный формат, который принимает встроенный auth-модуль Registry). Заодно Registry переведён с `docker run` на `docker-compose.yaml`, той же restart-политикой (`always`), что и раньше — не тихая замена поведения, а перенос существующей конфигурации в декларативный вид.

**Альтернативы:**
- *Отдельный CA только для Registry* — отклонено: весь смысл ADR-010 в том, что корень раздан один раз на все клиенты; заводить второй CA ради одного сервиса возвращает к проблеме, которую CA и должен был решить.
- *Token-based auth (JWT) вместо htpasswd* — ближе к тому, что делает production Registry (Harbor, Docker Hub), но требует отдельного auth-сервера. Избыточно для одного домашнего Registry с известным списком пользователей; рассматривается на будущее, если понадобится RBAC на уровне репозиториев (например, при переходе на Harbor).
- *Оставить без auth, закрыть только сетевым firewall (firewall zones)* — рассматривался как явный tradeoff. Отклонено в пользу TLS+auth: firewall zones ещё не реализованы, и до их появления Registry — единственный сервис с портом, открытым `0.0.0.0`, без какого-либо контроля доступа.

**Причина выбора TLS+auth:**
- переиспользование готовой CA-инфраструктуры — вся тяжёлая часть (раздача доверия клиентам) уже сделана при внедрении TLS для MinIO (ADR-010), для Registry понадобился только новый лист;
- не оставляет Registry единственным незащищённым сервисом после того, как MinIO уже на TLS;
- побочно устраняет отдельный технический долг — недекларативный `docker run` — без дополнительной задачи в очереди.

**Последствия:**
- `docker push`/`pull` требуют `docker login` с кредами из `registry_htpasswd`;
- конфигурация Registry воспроизводима из `docker-compose.yaml`, не зависит от истории команд в шелле;
- сертификат листа истекает через 1 год от даты выпуска — ротация по той же процедуре, что и для MinIO, без пересборки корня;
- Woodpecker CI и любые k3s-манифесты, ссылающиеся на Registry по `http://`, потребуют проверки после переключения — тот же урок, что с MinIO: сервер не поддерживает одновременно http и https.

**Проверка:** выполнено и подтверждено 28.07.2026. `docker logs registry` → `listening on [::]:5000, tls`. `openssl s_client -connect 192.168.1.10:5000 -CAfile homelab-root-ca.crt` → `Verify return code: 0 (ok)`. `docker login registry.homelab.local:5000` → `Login Succeeded`. Реальный `push`/`pull` тестового образа (`test-alpine`) прошёл через TLS и auth без ошибок. DNS-запись `registry.homelab.local` уже резолвилась на момент проверки.

**Дата истечения листового сертификата Registry: 28.07.2027.** Перевыпуск — по той же процедуре, что и для MinIO, без нового корня.

## ADR-012: Retain reclaim policy для критичных PV мониторинга

**Контекст:** 19.08.2026 обнаружено, что все четыре PV в namespace `monitoring` — Alertmanager, Prometheus (20Gi метрик), Loki, Grafana — используют StorageClass `nfs-storage` (provisioner `cluster.local/nfs-provisioner-nfs-subdir-external-provisioner`) с `reclaimPolicy: Delete`, без единого исключения. Удаление PVC — например, через `helm uninstall`, `kubectl delete pvc` или снос namespace — автоматически удаляет и сам PV, и физические данные на NFS-шаре Pi5. Backup для этих конкретных PV на момент обнаружения не существует — проверенный restore есть только для OpenBao и MinIO. Риск не гипотетический: одна случайная команда — и метрики за 140 дней, дашборды и алерты пропадают без возможности восстановления.

**Решение:** два независимых шага.
1. Немедленно: четыре существующих PV переведены на `Retain` точечным `kubectl patch` — без пересоздания, без даунтайма, без влияния на работающие поды.
2. На будущее: заведён отдельный StorageClass `nfs-storage-retain` — тот же provisioner и тот же физический NFS-экспорт на Pi5, что и у `nfs-storage`, разница только в `reclaimPolicy: Retain`. Дефолтный `nfs-storage` не тронут и остаётся `Delete`.

**Альтернативы:**
- *Поменять `reclaimPolicy` прямо в существующем `nfs-storage` на `Retain`* — отклонено: этим же StorageClass пользуются тестовые и временные workload, которые в homelab создаются часто; глобальный `Retain` означал бы, что каждый эксперимент оставляет мусор на NFS, требующий ручной уборки.
- *Ничего не делать до появления полноценного backup для этих PV* — отклонено: срок такой задачи не определён, а риск актуален прямо сейчас; `Retain` — дешёвая защита, не требующая ждать полноценного backup.
- *Longhorn или другой storage со встроенными snapshot'ами* — рассматривается отдельно как возможная замена NFS (единая точка отказа), но избыточное решение для этой точечной проблемы.

**Причина выбора двух StorageClass:**
- явное разделение по надёжности — «важное» не смешивается с «временным» в одном дефолтном поведении;
- изменение аддитивное: не трогает существующие PV, PVC или поды;
- переиспользует уже работающий provisioner и физический диск — не требует нового хранилища;
- дефолт остаётся удобным для экспериментов, критичное — через явный `storageClassName` (opt-in, а не opt-out).

**Последствия:**
- четыре существующих PV мониторинга защищены от каскадного удаления через reclaim policy;
- новые PVC на дефолтном `nfs-storage` по-прежнему получают `Delete` — новый критичный сервис в будущем нужно явно указывать на `nfs-storage-retain` в values.yaml/манифесте, иначе защиты не будет;
- `Retain` не заменяет backup: при удалении PVC данные остаются на NFS, но PV переходит в `Released` и требует ручного восстановления/переподключения — это защита от одной конкретной ошибки, а не стратегия disaster recovery;
- полноценный backup для этих PV остаётся отдельной открытой задачей.

**Проверка:** выполнено и подтверждено 19.08.2026. `kubectl get pv -o wide` — все четыре PV `monitoring` показывают `Retain`. `kubectl get storageclass` — `nfs-storage-retain` создан с тем же provisioner, что у `nfs-storage`; `nfs-storage` не изменён (`Delete`, дефолт для остального).

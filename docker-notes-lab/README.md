# Docker Notes Lab

Учебный проект вне основной инфраструктуры: API заметок на Flask и PostgreSQL, собранный для практики Docker, Compose и восстановления данных. Проверки выполнены на ноутбуке с Ubuntu; существующие сервисы homelab не менялись.

## Что внутри

- Python-приложение на Flask: создание и чтение заметок, проверка состояния базы;
- PostgreSQL 16 с данными в именованном томе Docker;
- Dockerfile для сборки образа приложения и Compose для запуска сервисов;
- SQL-схема и ручная проверка резервного копирования и восстановления.

## Основная идея

```text
curl → 127.0.0.1:5000 → app (Flask) → db (PostgreSQL) → том db_data
```

Compose соединяет сервисы внутренней сетью: приложение обращается к базе по имени `db`. Порт приложения доступен только на локальном интерфейсе хоста; порт базы на хост не опубликован. Контейнер приложения работает от непривилегированного пользователя.

## Запуск

Нужны Linux, Docker Engine, Compose plugin и `curl`.

1. В каталоге `docker-notes-lab` скопируй пример настроек, если `.env` ещё не создан:

   ```sh
   cp .env.example .env
   ```

2. В `.env` укажи пользователя, имя базы и свой учебный пароль. Файл `.env` и папка `backups/` исключены из Git. Переменные окружения не заменяют полноценное управление секретами; не публикуй пароль или дампы.
3. Запусти проект и проверь состояние:

   ```sh
   docker compose up -d --build
   docker compose ps
   ```

   Ожидается `healthy` для `db` и `app`. Если одноимённые переменные `DB_USER`, `DB_PASSWORD` или `DB_NAME` уже заданы в терминале, Compose использует их вместо значений из `.env`. Для запуска именно со значениями файла можно выполнить:

   ```sh
   env -u DB_USER -u DB_PASSWORD -u DB_NAME docker compose up -d --build
   ```

## Проверка API

```sh
curl -i http://127.0.0.1:5000/health
curl -i -X POST http://127.0.0.1:5000/notes \
  -H 'Content-Type: application/json' \
  -d '{"text":"Учебная заметка"}'
curl -i http://127.0.0.1:5000/notes
```

Ожидается `200` для `/health`, `201` и идентификатор для создания, затем `200` и список заметок. Пустой текст отклоняется с `400`.

Остановка проекта с сохранением тома:

```sh
docker compose down
```

`docker compose down -v` удаляет также том с данными. Не используй `-v`, если данные нужно сохранить.

## Резервная копия и проверка восстановления

Проверено 30.10.2026: SQL-дамп восстановлен в отдельном Compose-проекте и пустой базе; контрольная заметка прочитана через SQL. Рабочая база не использовалась как цель восстановления.

1. Создай папку и дамп. Команда перезапишет файл с тем же именем:

   ```sh
   mkdir -p backups
   docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB"' > backups/notes-backup.sql
   ```

   Проверь, что команда завершилась без ошибки и файл не пуст. Дамп содержит данные; не добавляй его в Git.

2. Подними отдельный тестовый проект и проверь его состояние:

   ```sh
   env -u DB_USER -u DB_PASSWORD -u DB_NAME docker compose -p notes-restore up -d db
   docker compose -p notes-restore ps
   ```

   Дождись `healthy`. Используй новую пустую тестовую среду: если `notes-restore` и база `restore_db` уже существуют после предыдущего теста, выбери другое имя проекта или базу с другим именем и измени его в командах ниже. Не удаляй том, пока не проверил его содержимое и назначение.

3. Создай пустую базу и восстанови дамп:

   ```sh
   docker compose -p notes-restore exec db sh -c 'createdb -U "$POSTGRES_USER" restore_db'
   docker compose -p notes-restore exec -T db sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d restore_db' < backups/notes-backup.sql
   docker compose -p notes-restore exec db sh -c 'psql -U "$POSTGRES_USER" -d restore_db -c "SELECT id, text FROM notes;"'
   ```

   Проверь наличие заранее созданной контрольной заметки. `ON_ERROR_STOP=1` останавливает восстановление при первой SQL-ошибке. Тестовый проект можно остановить командой `docker compose -p notes-restore down`; его том при этом сохранится.

## Диагностика: неверное имя хоста базы

30.10.2026 после проверки резервной копии значение `DB_HOST` приложения временно изменили с `db` на `db-wrong` и пересоздали только сервис `app`. Том базы не удалялся.

**Симптом:** `/health` отвечал `503`, хотя `db` оставался `healthy`. Логи приложения показывали повторные ответы `503`, но не содержали подробной ошибки подключения: обработчик возвращает общее сообщение.

**Проверка гипотезы:** внутри контейнера приложения проверили разрешение имени:

```sh
docker compose logs --tail 15 app
docker compose exec app python -c 'import socket; print(socket.getaddrinfo("db-wrong", 5432))'
docker compose exec app python -c 'import socket; print(socket.getaddrinfo("db", 5432))'
```

`db-wrong` вернул ошибку разрешения имени, а `db` разрешился успешно. Проверка показала проблему сетевого имени, а не проблему сборки образа или доказательство потери данных.

**Исправление:** в `compose.yaml` вернули `DB_HOST: db` и пересоздали приложение, не меняя базу:

```sh
env -u DB_USER -u DB_PASSWORD -u DB_NAME docker compose up -d --no-deps app
curl -i http://127.0.0.1:5000/health
curl http://127.0.0.1:5000/notes
```

После исправления `/health` вернул `200`, обе заметки остались доступны. Подробная причина ошибок БД в логах `/health` сейчас не отображается — это ограничение диагностики приложения.

## Ограничения

- Проект учебный: встроенный сервер Flask используется для разработки, не для production.
- Таблица из `schema.sql` создаётся при первой инициализации пустого тома; изменение файла не обновляет существующую базу автоматически.
- Именованный том не является резервной копией; дамп создаётся вручную и содержит данные на момент создания.
- Автоматический backup, внешнее хранение копий и полноценное управление секретами не реализованы.
- Ошибки подключения к БД в `/health` возвращают общее сообщение без подробной причины в логах.

# Security Baseline

Текущая базовая модель безопасности homelab. Документ фиксирует применённые настройки и отдельно отмечает то, что пока остаётся техническим долгом.

## Secrets and state

- Пароли Terraform передаются через чувствительные переменные и не хранятся в Git.
- `terraform.tfvars`, state и backup-данные исключены из публичного репозитория.
- Terraform state хранится в self-hosted MinIO через S3 backend.
- OpenBao используется как отдельный secrets manager; Kubernetes workloads получают секреты через Vault Agent Injector.
- Публичная документация содержит только имена объектов и пути без значений секретов, токенов и unseal keys.

## Proxmox API

Terraform подключается к Proxmox по HTTPS с включённой проверкой сертификата (`insecure = false`). CA Proxmox доверена на control node и не хранится в репозитории.

Для настройки порядка запуска VM была проверена модель прав Proxmox. Запрос с ролью Terraform на изменение `startup` получил `403` из-за отсутствия `Sys.Modify` на `/`. Расширять права токена только ради порядка запуска не стал: это нарушает least privilege.

Текущая политика:

- VM101–VM104: `on_boot = true`;
- VM105 (`ansible-control`): `on_boot = false`;
- `started = true` управляет состоянием VM после применения Terraform;
- блок `startup` не используется.

Такой вариант даёт автоматический запуск основных сервисных VM после старта Proxmox без выдачи Terraform полного системного права. Зависимый порядок запуска остаётся операционной процедурой, а не частью Terraform.

## SSH

В Ansible включён `host_key_checking = True`. Перед рабочим подключением fingerprints узлов проверяются и сохраняются в `known_hosts`. Отключение проверки допустимо только как временный диагностический шаг, но не является частью рабочего конфига.

## Automation account privileges

Учётка `ansible` изначально создавалась (`create-ansible-user.yml`) только с SSH-ключом, без sudo и без пароля — что подтвердилось 27.07.2026 при первой попытке использовать `become: true` в плейбуке раздачи CA: `Missing sudo password` на всех шести узлах.

Выдан `NOPASSWD` sudo на всех управляемых хостах (`/etc/sudoers.d/ansible-nopasswd`, `ansible ALL=(ALL) NOPASSWD:ALL`), проверено через `visudo -cf` перед записью на каждом узле. Bootstrap выполнен один раз вручную через `clai` (единственную учётку, у которой уже был рабочий sudo) — сам `ansible` не мог выдать права себе, потому что не имел ни одного пути стать root.

Осознанная модель: защита не в пароле, а в том, что вход под `ansible` возможен только по SSH-ключу (`~/.ssh/ansible_id`), который живёт на VM105. Кто угодно, зашедший под `ansible`, автоматически root — но зайти под `ansible` можно только с одной машины и с одним ключом.

Расхождение с `host_key_checking` закрыто 27.07.2026: возвращено `True` в `ansible.cfg` (см. фикс от 23.07 в `ansible-ssh-auth-incident.md`, который был кем-то откачен). `ansible all -m ping` прошёл на всех шести хостах без единого запроса подтверждения fingerprint — `known_hosts` уже был заполнен с прошлых сессий.

## k3s join token

Права на файл с токеном проверены и закрыты 28.07.2026 на обоих воркерах:

```
-rw------- 1 root root /etc/systemd/system/k3s-agent.service.env   # k3s-worker-01 (VM101)
-rw------- 1 root root /etc/systemd/system/k3s-agent.service.env   # k3-worker-2
```

Находка 06.07.2026 (токен в открытом виде в юнит-файле воркера) закрыта переносом в отдельный `.env` с правами `0600 root`. Непосредственная угроза утечки устранена.

**Оценка ротации (28.07.2026).** k3s использует один статический server-токен и для присоединения нод, и как PBKDF2-пассфраза для шифрования bootstrap-данных в datastore — токен нужен не только для входа новых нод, но и для восстановления кластера из снапшота. Токен не истекает сам по себе.

Официальная процедура — `k3s token rotate --new-token <новый>`, после чего все серверы и агенты, подключённые по старому токену, требуют перезапуска с новым (`k3s.service` на мастере, `k3s-agent.service` на обоих воркерах).

Важное ограничение: снапшоты/бэкапы datastore, снятые **до** ротации (у нас — `k3s-server-backup-2026-07-06.tar.gz`), при восстановлении требуют старый токен. Ротация не должна отбрасывать старое значение — старый токен сохраняется отдельно (KeePassXC), привязанным к дате конкретного бэкапа, либо сразу после ротации снимается свежий бэкап datastore под новый токен.

Рестарт `k3s.service` на мастере (`homelab`, Pi5) подчиняется тому же правилу, что апгрейд control plane — `frpc` живёт на том же узле, выполнять только при физическом доступе.

**Решение:** поскольку права на файл уже закрыты и непосредственный вектор утечки устранён, немедленная ротация не критична. Учтено как плановый hardening, не как открытая уязвимость. Выполнить при следующем локальном заходе: `k3s token rotate` → обновить токен на обоих воркерах → перезапустить агентов → перезапустить сервер на мастере → снять свежий бэкап datastore → сверить старый токен сохранён в KeePassXC.

## Network boundaries

- Домашняя сеть находится за NAT.
- Удалённый доступ проходит через FRP и VPS.
- Публикация сервисов выполняется через явно настроенные ingress и DNS-имена.

## Registry TLS и auth

Закрыто 28.07.2026 (см. [ADR-011](../decisions.md#adr-011-tls-и-basic-auth-для-docker-registry) и [registry-tls-auth.md](registry-tls-auth.md)). Registry переведён на TLS (сертификат от internal CA, ADR-010) и `htpasswd`-auth (bcrypt). Подтверждено фактом: `openssl s_client` — `Verify return code: 0 (ok)`, реальный `push`/`pull` через TLS с авторизацией. Заодно переведён с голого `docker run` на `docker-compose.yaml`.

Известный мелкий долг: креды `docker login` хранятся в `~/.docker/config.json` в base64, не в зашифрованном виде — стандартное поведение Docker CLI без credential helper. Принято осознанно, не блокирует.

## Deferred hardening

Следующие задачи не выдаются за выполненные:

- Offsite backup копируется вручную; автоматическое расписание и контроль свежести ещё не реализованы.
- Один k3s control plane и NFS остаются точками отказа homelab.
- Ротация k3s join-токена оценена и задокументирована, но не выполнена — плановый hardening, не открытая уязвимость (см. раздел «k3s join token» выше).

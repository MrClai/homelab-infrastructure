# Infrastructure Change Validation

Документ описывает минимальный порядок внесения изменений в homelab. Цель — отделить изменение конфигурации от подтверждения фактического состояния и не считать успешный запуск команды достаточным результатом.

Проверки текущего состояния сервисов вынесены в [Operations](../operations.md). Здесь остаются только действия до и после изменения, критерии остановки и специфичные для изменения проверки.

## Terraform

Рабочий каталог: `terraform/` на control node.

Перед изменением:

```bash
terraform fmt -check -recursive .
terraform init
terraform validate
terraform plan
```

Ожидаемый результат для уже синхронизированной инфраструктуры:

```text
No changes. Your infrastructure matches the configuration.
```

Если plan содержит неожиданный `destroy`, замену VM или изменение диска, применение останавливается. Для изменения автозапуска ожидается только in-place update поля `on_boot`.

После `apply` проверяются оба источника состояния:

```bash
terraform plan
qm config <VMID> | grep -E '^(name|onboot|startup):'
```

Terraform подтверждает соответствие конфигурации, а `qm config` подтверждает фактическую настройку Proxmox. Блок `startup` в текущей политике не используется.

## Ansible

Рабочий каталог: `ansible/` на VM105 (`ansible-control`). Перед изменением проверяются inventory и доступность управляемых узлов. После изменения запускается read-only healthcheck. Команды и ожидаемый результат находятся в разделе [Ansible документации Operations](../operations.md#ansible).

Успех означает, что Ansible подключается по SSH с проверкой host key и выполняет модуль на каждом хосте. `ansible -m ping` не является ICMP-проверкой.

## Kubernetes

После инфраструктурных изменений выполняются проверки из раздела [Kubernetes документации Operations](../operations.md#kubernetes).

Критерии приёмки изменения:

- все узлы имеют ожидаемый статус и версию;
- после изменения не появились новые неработающие pod;
- Traefik, ArgoCD и затронутые endpoint-ы доступны;
- при ошибке проверены логи компонента и его повторное состояние.

## Stop conditions

Работа останавливается до применения, если:

- plan предлагает удаление или пересоздание существующей VM;
- Terraform не может проверить TLS Proxmox;
- fingerprint SSH-хоста не совпадает с ранее проверенным;
- healthcheck показывает недоступный узел;
- после изменения Kubernetes появляются новые неработающие pod или ломается ingress.

После каждой существенной операции фиксируются дата, ожидаемое изменение, фактический результат и команда проверки. Секреты, токены и значения переменных в документ не записываются.

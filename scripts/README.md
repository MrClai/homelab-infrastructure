# Backup Scripts

Скрипты для backup критичных данных homelab — OpenBao (секреты) и MinIO (object storage, включая Terraform state).

## Почему именно эти два сервиса

Gitea, Prometheus и большинство остальных сервисов либо легко пересоздаются из кода (GitOps, IaC), либо данные дублируются в нескольких местах (например, репозитории Gitea зеркалятся на GitHub). OpenBao и MinIO — единственные сервисы, где данные существуют в одном экземпляре без дублирования, поэтому именно они в фокусе backup-стратегии.

**Отдельный открытый вопрос — критичные NFS PV** (мониторинг: Alertmanager, Prometheus, Loki, Grafana, все на `nfs-storage-retain`). `reclaimPolicy: Retain` защищает только от случайного удаления PVC/релиза — не от отказа диска на Pi5 или порчи файлов. Backup для них пока не реализован, это отдельная задача (нужен CronJob в кластере или Velero, а не host-level скрипт, как здесь).

## Архитектура

```
OpenBao ──┐
          ├──► MinIO bucket backups/.. (backups/openbao/, backups/minio-self/)
MinIO ────┘
                 │
                 ▼
    offsite-копия на ноутбуке: fetch-backups-to-laptop.sh, забирает bucket
    backups/ через mc mirror (S3 API, вручную, из домашней сети)
```

Важно про порядок: OpenBao-снапшот попадает в offsite-копию только если backup-minio.sh запущен ПОСЛЕ backup-openbao.sh (mc mirror в backup-minio.sh снимает срез бакетов через API — снапшот OpenBao должен успеть туда попасть заранее).

## Скрипты

- **`backup-openbao.sh`** — снимает Raft snapshot OpenBao (`bao operator raft snapshot save`) и загружает в MinIO вместе с sha256-checksum. Использует встроенный snapshot-механизм, а не сырое копирование файлов — это важно для consistency, так как Raft использует журнал транзакций.
- **`backup-minio.sh`** — снимает данные всех бакетов MinIO (кроме самого backup-бакета) через `mc mirror`, то есть через S3 API, а не сырым `tar` файлов с диска: раньше архив мог получиться битым, если MinIO в момент архивации писал в те же файлы, что читал `tar`. Архивирует снятое, считает checksum, грузит в отдельный backup-bucket.
- **`fetch-backups-to-laptop.sh`** — забирает содержимое bucket `backups/` (оба типа бэкапов + checksum-файлы) через `mc mirror` на локальную машину как offsite-копию, проверяет checksum каждого файла. Запускается вручную, при физическом подключении к домашней сети.

Общее для всех трёх скриптов:
- **Checksum.** Каждый артефакт бэкапа сопровождается файлом `<имя>.sha256` (sha256sum, без соли — этого достаточно для detect corruption, не для defense от подмены). Проверка: `sha256sum -c <файл>.sha256`. `fetch-backups-to-laptop.sh` делает это автоматически при каждом запуске.
- **Retention.** Три уровня хранения, каждый со своим сроком: локальный буфер на сервере перед загрузкой (7 дней, переменная `RETENTION_DAYS_LOCAL`), сам бэкап-бакет в MinIO (30 дней, `RETENTION_DAYS_REMOTE`, чистится через `mc rm --older-than`), offsite-копия на ноуте (90 дней по умолчанию, `RETENTION_DAYS_LOCAL` env var в `fetch-backups-to-laptop.sh`).
- **Сигнал ошибки.** `set -euo pipefail` останавливает скрипт при первой же ошибке. `backup-openbao.sh` и `backup-minio.sh` дополнительно пишут машинно-читаемый статус последнего запуска в `/var/log/homelab-backups/<сервис>.status` (timestamp/result/detail) — на случай неожиданного падения через `trap ... ERR`, а не только при явных проверках. Это подготовка к переходу на cron: пока запуск ручной, файл можно просто прочитать глазами; на cron его стоит забирать через node_exporter textfile collector или аналог, чтобы получить алерт в уже поднятом Alertmanager, а не узнавать о падении бэкапа через месяцы.

## Перед использованием

1. Установи MinIO client (`mc`) на машине, откуда запускаешь backup-скрипты (Pi5, VM104, **и теперь также на ноутбуке** — `fetch-backups-to-laptop.sh` больше не использует scp).
2. Настрой alias: `mc alias set homelab https://<MINIO_HOST>:<API_PORT> <ACCESS_KEY> <SECRET_KEY>`. Уточни реальный API-порт через `docker ps` — он может отличаться от дефолтного 9000 в зависимости от маппинга портов. С 27.07.2026 MinIO работает только по TLS (см. ADR-010) — клиент должен доверять `homelab-root-ca.crt`, иначе `mc` откажет в подключении с ошибкой сертификата. Это правило теперь касается и ноутбука, не только серверов.
3. Убедись, что `/var/log/homelab-backups` доступен для записи на VM104 и Pi5 (или поменяй `STATUS_DIR` в скриптах).

`fetch-backups-to-laptop.sh` больше не требует `PI5_HOST` / SSH-доступа — переменная удалена, так как скрипт теперь ходит в MinIO напрямую через `mc`, а не по scp на диск Pi5.

## Restore

Оба типа backup проверены restore-тестами в изолированных окружениях, не затрагивая прод:

- **OpenBao** — Raft snapshot восстановлен в отдельный Docker-инстанс:
  init и unseal проходят, Raft committed index подтверждает наличие
  реальных данных в снапшоте.
- **MinIO** — архив распакован, содержимое (структура `<бакет>/<объект>`, снятая через `mc mirror`) залито обратно через `mc mirror` в тестовый MinIO-инстанс на нестандартных портах: бакеты видны, `terraform.tfstate` читается как валидный JSON (`mc cat`).
  ⚠️ Формат архива поменялся вместе с переходом на `mc mirror` (раньше — сырой слепок `/mnt/minio`, теперь — объекты через API). Старый restore-тест валиден для старого формата; **новый формат архива restore-тестом ещё не перепроверен** — сделать перед тем, как полагаться на первый бэкап, снятый новой версией скрипта.

Данные в бэкапе соответствуют моменту снятия: изменения после backup при restore теряются — учитывать при выборе точки восстановления.

## Offsite

Первый успешный прогон fetch-backups-to-laptop.sh — 02.07.2026: архив скачан из домашней сети на локальную машину (WSL).
Запуск ручной; расписание — в планах (когда появится, машинно-читаемый `.status` из backup-скриптов пригодится для алертинга).

## Известные пробелы (не закрыты этой правкой)

- **Backup критичных NFS PV** (monitoring stack) — не реализован, отдельная задача уровня кластера.
- **Расписание запуска** — всё ещё ручное; после автоматизации через cron нужно решить, куда именно смотрит алертинг (`.status` файлы уже готовы как источник).
- **Checksum без защиты от подмены** — sha256 без подписи защищает от битого архива, но не от намеренной подмены файла в MinIO кем-то с доступом к бакету. Для этого homelab пока избыточно, но стоит иметь в виду.
